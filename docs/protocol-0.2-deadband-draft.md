# 协议 0.2 草案：deadband 差值上报 + 心跳兜底

状态：设计稿（2026-10-04，依据优化报告 #4）；随 ESP32 固件一并实现与验收。
依据：优化调研报告（私有目录）——工业侧 UMH 的 dead-band
（内置可配心跳）与学术侧 Miskowicz 的 send-on-delta 双重背书；稳态消息量可降一个数量级，
电池设备为必选项。

## 1. 设计原则

1. **不升 proto_ver**：本特性全部通过 discovery 里**新增可选字段**表达，旧设备不填即维持
   周期上报，中枢零改动（协议 §10：新增可选字段向后兼容）。
2. **心跳是底线**：差值上报可能让设备长时间沉默，必须配心跳，否则 retain 值陈旧、
   last_seen 看门狗误判离线。

## 2. discovery 扩展（可选字段）

```json
{
  "proto_ver": 1,
  "device_id": "sensor-esp-01",
  "reporting": {
    "heartbeat_s": 60,
    "deadband": { "temperature": 0.5, "humidity": 2 }
  }
}
```

| 字段 | 必填 | 语义 |
|------|------|------|
| `reporting.heartbeat_s` | ✔（声明 deadband 时） | 任一属性两次发布之间的最大间隔秒数 |
| `reporting.deadband` | ✘ | 键值对：属性 key → 触发阈值（数值型属性的绝对差） |

未声明的属性按设备自己的默认周期上报（v0.1 行为）。

## 3. 设备端规则（MUST）

1. 属性值与**上次已发布值**之差 > `deadband[key]` → 立即发布（仍 retain）。
2. 距任一属性上次发布 ≥ `heartbeat_s` → 无论值是否变化都发布一次（保活心跳）。
3. `heartbeat_s` 必须 ≪ 中枢 `staleOfflineMinutes`（默认 15 分钟），建议 ≤ 其 1/3；
   固件模板里写死校验。
4. 上线三连（discovery → status → 首拍遥测）不变；中枢已有重排缓冲兜乱序。

## 4. 中枢与手机端影响

- 中枢：**零改动**。消息变少而已；看门狗靠 heartbeat_s 保证不误杀。
- 手机端：零改动（SSE 本来就是事件驱动）。
- AI 编排（agent）：零改动（查状态走 `lab_get_device_state` 读最新值）。

## 5. 验收清单（固件实现后）

- [ ] 稳态（恒温箱）下消息频率 ≈ 1/heartbeat_s，而非 1/原周期
- [ ] 阶跃（手捏传感器）后 ≤1 个上报周期内发出差值消息
- [ ] 连续静默 3×heartbeat_s，中枢在线状态仍为在线（看门狗不误杀）
- [ ] 设备重启后 retain 值时间戳新鲜
- [ ] 电池设备实测平均电流对比（论文 M 指标可用）

## 6. 后续（0.3+ 候选，不在本稿范围）

- 按属性类型扩展阈值（枚举型：变化即报；布尔型：翻转即报）

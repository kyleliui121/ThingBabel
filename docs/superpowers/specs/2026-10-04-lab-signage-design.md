# 实验室展示屏管理系统 — 设计文档

日期：2026-10-04
状态：已与需求方确认的设计稿

## 1. 背景与目标

实验室门外有一台安卓 7 系统的电视机，上面运行一个已有的"成果展示"应用（跨端/网页壳实现，代码在手可修改）。目前更新展示内容需要到电视机上手动操作。

**项目目标**：做一个三端系统，实现"手机远程管理电视展示内容"：

- 电视端：循环展示实验室成果内容（第一版：图片轮播 + 文字标题）
- 手机管理端（安卓 APK）：上传、编辑、排序、启用/停用展示内容
- 后端：跑在实验室一台常开电脑上，负责存储与分发

**项目性质**：学习练手项目（第一个完整项目），因此优先保证**做完**，其次是覆盖真实的全栈工程能力（REST API、文件上传、SQLite、轮询与缓存、APK 打包、三端联调）。

## 2. 需求范围

### 2.1 功能需求（第一版）

1. 手机端登录（密码 + token）
2. 内容管理：新建（图片/文字）、编辑、删除、排序（上移/下移）、启用/停用
3. 电视端自动同步：内容变更后 30 秒内自动刷新展示
4. 电视端离线兜底：断网或后端不可用时继续展示本地缓存的内容
5. 后端开机自启、崩溃自动拉起

### 2.2 非目标（第一版明确不做）

- 视频播放（如确认需要，升入第一版）
- 定时排期（如"工作日 9:00-18:00 展示"）
- 多用户、角色权限
- 多屏幕管理
- 程序（APK）远程升级
- 公网访问 / 云部署（本系统仅限实验室内网使用）

## 3. 总体架构

```
┌─────────────────┐      HTTP       ┌──────────────────────┐      HTTP轮询      ┌────────────────┐
│  手机管理端      │ ──────────────→ │  后端服务              │ ←──────────────── │  电视展示端      │
│  uni-app 打APK  │  上传/编辑/排序  │  Node.js + Express    │  每30秒检查版本    │  现有网页壳改造  │
└─────────────────┘                 │  + SQLite (实验室电脑) │ ────────────────→ └────────────────┘
                                    └──────────────────────┘   /uploads 静态图片
```

三端职责单一：

- **手机端**只负责内容编辑（调用管理 API）
- **后端**只负责存储、鉴权、分发
- **电视端**只负责拉取内容并展示（只读 API）

网络环境：三者处于实验室同一内网 WiFi。后端电脑在路由器上做 DHCP 静态绑定（固定内网 IP），手机端首次使用时填一次地址。

## 4. 后端设计

### 4.1 技术栈

| 组件 | 选型 | 说明 |
|------|------|------|
| 运行时 | Node.js LTS (20+) | |
| Web 框架 | Express 4 | |
| 数据库 | better-sqlite3 | 单文件数据库，零配置，`data.db` 一个文件即全部数据 |
| 文件上传 | multer | 磁盘存储，白名单校验 |
| 鉴权 | jsonwebtoken | JWT，7 天有效期 |
| 守护 | pm2 | 崩溃自动重启 + 开机自启 |

### 4.2 数据模型

表 `contents`：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PRIMARY KEY AUTOINCREMENT | |
| type | TEXT NOT NULL | `image` / `text` |
| title | TEXT NOT NULL | 标题（文字页或图片页叠加显示） |
| body | TEXT | 文字内容（type=text 时使用） |
| file_path | TEXT | 图片相对路径（type=image 时使用，如 `uploads/abc123.jpg`） |
| sort_order | INTEGER NOT NULL | 展示顺序，越小越靠前 |
| enabled | INTEGER NOT NULL DEFAULT 1 | 1=启用 0=停用 |
| created_at | TEXT | ISO 时间 |
| updated_at | TEXT | ISO 时间，任何修改都刷新 |

表 `settings`：键值对，其中 `content_version`（INTEGER）在每次内容发生增删改/排序/启停时自增。电视端用它判断是否需要重新拉取。

配置文件 `config.json`：`{ "port": 3000, "adminPassword": "..." }`。

### 4.3 API 设计

管理端接口（需 `Authorization: Bearer <token>`）：

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/login` | body: `{password}`；正确返回 `{token}`，错误返回 401 |
| GET | `/api/contents` | 全量列表（含停用），按 sort_order 排序 |
| POST | `/api/contents` | multipart：`title`、`type`、`body`（text 时）、图片文件（image 时）；成功返回新记录 |
| PUT | `/api/contents/:id` | JSON：`title`/`body`/`enabled` 或 `move: "up" \| "down"`（与相邻项交换 sort_order）；更换图片走 POST multipart 到 `/api/contents/:id/image` |
| DELETE | `/api/contents/:id` | 删除记录并删除对应文件（幂等） |

电视端接口（内网、不鉴权）：

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/display/version` | 轻量：`{version}`，电视端每 30 秒轮询 |
| GET | `/api/display` | 全量：`{version, items}`，items 为启用中的内容按 sort_order 排序，图片字段给出完整 URL |

静态文件：`GET /uploads/:filename`，Express.static 服务。

统一响应：成功 `{code: 0, data: ...}`；失败 `{code: <非0>, message: "..."}`，HTTP 状态码相应设置（400 参数错、401 未登录、404 不存在、500 服务器错）。

### 4.4 文件上传规则

- 白名单扩展名：`.jpg .jpeg .png .gif .webp`
- 单文件上限 10MB
- 存储文件名：`<uuid><扩展名>`，避免重名与路径注入
- 删除内容时同步删除文件，文件不存在不报错

## 5. 手机管理端设计（uni-app）

- 框架：uni-app（Vue 3），HBuilderX 云打包 APK，Android 目标版本兼容到能装当前主流手机
- 页面：
  1. **登录页**：输入后端地址（如 `http://192.168.1.100:3000`）+ 密码。地址与 token 存本地 storage；请求失败给出明确提示（连不上 / 密码错）
  2. **内容列表页**：每项显示缩略图/文字摘要、启用开关、上移/下移、编辑、删除（删除需二次确认）；顶部显示当前后端地址，可点击修改
  3. **编辑页**：新建/编辑复用。type=image 时选图（uni.chooseImage）+ 标题；type=text 时标题 + 正文
- 网络层：封装统一 request 模块，自动带 token；401 时跳回登录页
- 真机调试：HBuilderX 标准基座即可，打包用云打包

## 6. 电视端改造设计

现有壳加载的网页是改造对象。改造分两种情况，**实施第一步先确认壳的类型**再定：

- **情况 A（uni-app/5+ 壳，有 plus API）**：图片通过 `plus.downloader` 下载到本地缓存目录后展示，实现真正离线可用
- **情况 B（纯 WebView 加载本地网页）**：图片直接 HTTP 加载，清单存 localStorage 兜底

轮询逻辑（两情况相同）：

```
启动 → 读本地缓存（清单+版本）→ 有缓存先播缓存
     → GET /api/display 全量拉取成功则替换缓存并刷新展示
每 30 秒 → GET /api/display/version
         → version 与本地一致：无操作
         → 不一致或请求失败：失败则静默继续播当前内容，下轮再试
         → 一致后拉全量 → 更新缓存 → 重建轮播列表
```

展示形式：全屏图片轮播（5 秒/张）+ 底部标题叠加；type=text 的条目渲染为文字页（深色底、大字号）。具体视觉按现有展示页风格延续，不追求重设计。

## 7. 错误处理汇总

| 场景 | 处理 |
|------|------|
| 电视断网 / 后端关机 | 继续播缓存内容，轮询静默重试，恢复后自动同步 |
| 电视冷启动且无缓存 | 显示"等待连接"占位页，连上后进入正常展示 |
| 后端崩溃 | pm2 自动重启；SQLite 单文件 + 上传文件落盘，重启无数据丢失 |
| 手机端连不上后端 | 提示"无法连接 <地址>，请检查网络或地址"，不崩溃 |
| 手机端 token 过期（401） | 清 token，跳登录页 |
| 上传超限 / 非法格式 | 后端 400，手机端 toast 提示原因 |

## 8. 测试与验收标准

1. 后端接口先用 curl/Postman 全部验证（登录、CRUD、排序、上传限制、display 接口）
2. **端到端验收**：
   - 手机上传一张图 → 电视 30 秒内自动开始轮播该图
   - 手机停用/删除 → 电视同步消失
   - 手机排序 → 电视轮播顺序一致
   - 关闭后端 → 电视继续播缓存；重启后端 → 电视自动恢复同步
   - 后端电脑重启 → 服务自动恢复，无需人工干预
3. 真机验证：APK 在目标安卓手机上安装、登录、全流程操作正常

## 9. 部署与运维

- 后端目录：实验室电脑上固定目录（如 `D:\lab-signage-server`），`pm2 start app.js --name signage` 守护
- 开机自启：Windows 计划任务执行 `pm2 resurrect`（或 pm2-windows-startup）
- 后端电脑 IP 固定：路由器 DHCP 静态绑定
- 数据备份：`data.db` + `uploads/` 即全部数据，偶尔复制一份即可

## 10. 后续迭代方向（按需）

1. 视频支持（type=video，轮播时按时长播放）
2. 定时排期（contents 加 publish_from/publish_to）
3. 多屏幕（display 接口按 screen_id 区分）
4. 拖拽排序、内容预览、展示日志

## 11. 实施注意事项

- 第一步先确认电视壳的技术形态（情况 A/B），这决定电视端改造的具体路径
- 电视是安卓 7（API 24/25），改造后的网页所用 JS 特性需兼容（避免过新的语法；uni-app 编译产物本身向下兼容）
- better-sqlite3 为原生模块，实验室电脑需能正常安装 Node 工具链；若安装受阻，退化方案为 sql.js（纯 WASM）或改用 lowdb（JSON 文件），API 层不变
